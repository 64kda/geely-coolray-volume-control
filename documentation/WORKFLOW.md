# Обязательный процесс разработки фич

Уточнение пользователя от 12.11.2026 для проекта «Регулятор громкости».

1. Основной агент читает правила, код и текущую заметку задачи, проверяет Git и определяет критерии приёмки. Сохраняет существующие изменения.
2. При разработке каждой фичи обязательно применяет установленные навыки ub-mode и TokenEconomizer. ub-mode: First Make it Work → Then Make it Right → Follow Practice; минимальные проверяемые этапы и тест воспроизведения, когда он практичен. Недоступные инструменты отмечает явно.
3. TokenEconomizer остаётся включённым. Диагностика — через Windows-обёртку с --cwd фактического корня проекта. Сохраняются настройки и ограничения проекта. Агент не выдаёт доверие hooks и не считает установку доказательством их работы. Недоступность диагностики фиксирует; экономия не отменяет обязательных проверок.
4. Основной агент составляет план, реализует этап, выполняет тесты, сборку и проверку APK. Локальные тесты, эмулятор API18 и приёмка на магнитоле учитываются отдельно.
5. Критик проверяет существенные изменения по AGENTS.md после собственных проверок основного агента. При высоком риске отдельно проверяет план до реализации. Бюджет обычно один вызов, максимум два, включая план. Критик не редактирует файлы и не делегирует. Основной агент проверяет замечания, исправляет подтверждённые проблемы и повторяет затронутые проверки. Другие исполнители автоматически не подключаются.
6. До финального отчёта обязательно фиксировать итоги каждого этапа в Obsidian: изменения и причины решений, APK и версию, фактические результаты проверок, итог критика и ограничения, применение ub-mode и состояние TokenEconomizer, открытые вопросы и следующий шаг. Обновлять отдельную заметку/раздел фичи, статус и при новом APK страницу релиза/реестр; сохранять навигационную ссылку из плана.
7. При работе с Obsidian обязательно применять установленные obsidian-cli и obsidian-markdown; при работе с .base — obsidian-bases, с .canvas — json-canvas. Использовать vault «64KDA Space», читать точную заметку перед изменением, сохранять окружающее содержимое. После записи перечитать и проверить результат. При недоступности Obsidian сохранить локальный отчёт и явно оставить перенос открытым.
8. Основной агент выдаёт результат со ссылками на заметки и артефакты. Автомобильная приёмка не объявляется выполненной без доказательств. Коммиты, push и публикация — только по отдельному поручению пользователя.

Последовательность: пользователь → основной агент (контекст, навыки, план) → критик плана при высоком риске → основной агент (реализация и проверки) → критик результата по AGENTS.md → основной агент (исправления, повторные проверки, Obsidian, проверка записи) → пользователь.

## Дизайн

Для задач, где нужно придумать дизайн, нарисовать/выбрать макеты или провести ревью собранного приложения, обязательно применять установленный навык `design-review` из https://github.com/humbleteam/design-review. Читать его SKILL.md и обязательную references/review-rubric.md перед обзором.

- При поиске дизайна использовать advisory mode для конкретного вопроса о компоновке или взаимодействии; при наличии экранов — grounded advisory mode.
- При создании макетов использовать подходящий установленный навык создания визуалов (Product Design/ImageGen по задаче), затем design-review для проверки макета или сравнения вариантов до реализации. Сам design-review не рисует изображения.
- Для ревью собранного приложения сначала получить снимки фактического интерфейса с указанием APK/версии, устройства или эмулятора и проверенных состояний. Затем выполнить design-review; исправить подтверждённые замечания и повторить затронутые проверки/снимки. Если запуск недоступен, прямо отметить, что ревью собранного приложения не выполнено; макет не заменяет runtime.
- Рекомендации адаптировать к Android 4.3/API18 и экрану магнитолы, не переносить автоматически современные веб-требования или новые Android API. Оценка скриншотов не подтверждает работу жестов, звука и boot/wake.
- Итог дизайн-проверки, источники снимков, принятые/отклонённые замечания и ограничения фиксировать в заметке фичи Obsidian. Дизайн-проверка выполняется основным агентом и не заменяет обязательного критика; дополнительные агенты автоматически не запускаются.

Последовательность для UI-фичи: дизайн-вопрос → варианты/макеты → design-review → реализация → сборка и runtime-снимки → design-review → исправления и проверки → критик по AGENTS.md → Obsidian и проверка записи → отчёт.
